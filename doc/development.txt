Development baseline

Build policies originate from public blofeld-emu revision
057d3411b88b746c8bbf97c69958054e8a77d509 and are listed in THIRD_PARTY.txt.
Processor and board behavior require independent Lead A1 evidence.

Owned C++ headers live beside their implementations under src/. Includes use
module paths relative to src/; internal ARM helpers have distinct names.

First integration sequence
1. Obtain the reconstruction project's evidenced format/architecture inventory
   for both parts; track unresolved regions and exact input identities.
2. Select appropriate CPU/DSP backends, pin source revisions/licenses and native
   instrumentation before integration. Require independent instruction vectors.
3. Build a fail-visible board map and deterministic scheduler from actual guest
   accesses, implementing one observed startup frontier at a time.
4. Extract observable parameters from original firmware state and publish the
   documented snapshot contract outside the time-critical path. Establish table
   names/ranges/scaling only where supported; retain raw values when unresolved.
5. Advance original boot, MIDI/USB/audio, storage and update/recovery tests, then
   qualify complete functions, ordinary host playback and hardware comparisons.

Quality commands
  python3 tools/dependencies.py --fetch --ghidra
  cmake --preset strict
  cmake --build --preset strict
  cmake --build build/strict --target quality
  xvfb-run -a dbus-run-session -- /usr/bin/python3 test/gui_smoke.py

Builds are offline and do not need originals or private GitHub access.
Original checks verify bundle/section/kernel identities for every selected
native group. CTest registers each native program independently; SPI has two
controller cases, two first-uploader-handshake cases and all four part/transport
kernel cases, plus four initial-profile kernel transfers with actual per-word
RAM grants and no DSP activation. Each retains its complete assertions, guest
instruction bounds and normal per-test time bound.
The original script's aggregate native interface remains available for manual
runs. Synthetic checks require no manufacturer inputs.

The quality target runs format, CTest and Python bootstrap regressions. Optional
reference identity checks skip explicitly if local originals are absent.
GTK integration runs separately and requires GTK4 plus an isolated display.
release retains strict checks; thread is for future separate concurrency testing.
Optional VisualDSP++5.1.2 target references and the isolated Wine installation
are described in visualdsp.txt; they are not normal build dependencies. The
current missing vendor license prevents assembler/simulator qualification.
miniLZO is built from pinned upstream source for safe container decoding, with
native sanitizers/hardening. Native SLEIGH executes an ARM-state reference
fixture with an owned status/bank adapter; system/interrupt/board qualification
remains pending. No Blofeld
CPU model is imported. Future fuzz harnesses run only
on explicit user request.

Performance choices
SSE4/AVX2/AVX-512 mapping and execution across multiple host cores are options delegated
to implementation judgment, not additional user requirements. First identify
actual DSP programs, numerical modes and communication boundaries. Profile
guest workloads and a faithful reference before choosing SIMD/JIT or parallel
workers. Preserve guest rounding/saturation/extended precision and causal
emulated-time ordering; compare accelerated paths with the reference and use
separate TSan once concurrent native code exists. Do not infer real-time
performance from a vendor clock rating or a synthetic instruction benchmark.
The local i5-1135G7 reports SSE4.1/4.2, AVX2 and AVX-512 features through lscpu.
This provides a comparison host, not a deployment requirement. Any accelerated
backend needs runtime CPU/OS capability checks and a qualified fallback; select
vector width from end-to-end workload measurements, not advertised lane count.
